# Switching the site to a new ESO update

Each game update lives under its own path prefix (`/u50/`, `/u51/`). Only the
update named by `current_update` in `data/update_config.json` is regenerated by
the hourly cron; every other update is served from whatever is committed under
`output/<prefix>/`. Two things follow from that and both have bitten us:

1. **Freeze before you flip.** The cron never commits generated pages. The day
   `current_update` changes, the previous update's live pages are replaced by
   the repo copy. U49 was archived with the pages from its activation day
   because nobody committed the final state first.
2. **Pin the ESO Logs partition.** ESO Logs ranks per update ("partition") and
   defaults to the newest one. Every update in the config must carry its
   `partition` id, otherwise the scanner silently publishes the new update's
   logs under the old prefix from launch day on (U51 under `/u50/`, Sept 2026).

## 0. Find the new partition id

```bash
python3 - <<'PY'
import os, requests
tok = requests.post("https://www.esologs.com/oauth/token", data={"grant_type": "client_credentials"},
                    auth=(os.environ["ESOLOGS_ID"], os.environ["ESOLOGS_SECRET"])).json()["access_token"]
q = "{ worldData { zone(id: 1) { partitions { id name compactName default } } } }"
print(requests.post("https://www.esologs.com/api/v2/client", json={"query": q},
                    headers={"Authorization": f"Bearer {tok}"}).json())
PY
```

Partitions are global, so any trial zone works. The entry with `default: true`
is the live update.

## 1. Rebuild the outgoing update one last time

Rankings for old partitions stay queryable, so a full rescan pinned to the
outgoing partition gives the definitive end-of-update leaderboard. Scan from a
worktree on a non-main branch so the scan's output lands in `output-dev/`:

```bash
git worktree add -b tmp/freeze /tmp/freeze main
cd /tmp/freeze
python -m src.eso_build_o_rama.main --update-version u50        # all 14 trials, ~50 min, ~3,400 API points
python scripts/deployment_check.py output-dev/u50               # must pass
```

Expect the hourly API budget (3,600 points) to run out near the end; the client
backs off and retries, and a handful of mundus lookups may be lost. Compare
against the `builds-json-<prefix>` artifact of the last good run (30-day
retention); it can also be replayed with `--regenerate-only` if ESO Logs is
unavailable.

## 2. Regenerate the pages in production mode and freeze them

Pages generated under `output-dev/` carry development markers (`[DEV]` titles,
github.io canonical URLs, `-dev` social previews), because the generator keys
development mode off the output directory name. Only the data from step 1 is
reused; the pages are regenerated from the main tree, which writes straight
into the freeze location:

```bash
cd <main checkout, on main>
mkdir -p output/u50 && cp /tmp/freeze/output-dev/u50/builds.json output/u50/
python -m src.eso_build_o_rama.main --update-version u50 --regenerate-only   # seconds
find output/u50/static -name '*-dev*' -delete                                # dev previews copied from static/
python scripts/deployment_check.py output/u50                                # must pass
grep -l 'brainsnorkel.github.io/eso-build-o-rama/u50\|\[DEV\]' output/u50/*.html | wc -l   # must be 0
git checkout -- output/index.html output/updates.html                        # root pages are regenerated by CI
git add output/u50 && git add -f output/u50/builds.json output/u50/*.csv
git commit -m "feat(u50): freeze Update 50 archive"
```

`.gitignore` excludes `*.json` and `*.csv`, so `builds.json` and the CSV
downloads must be force-added or the live `/u50/builds.json` goes 404 on the
first deploy of the new update. Stage the directory explicitly; never
`git add -A` in this repo. Expect ~145 MB and ~2,300 files, mostly
`static/icons`; the pages reference `static/...` relative to the prefix, so
the per-update static copy is required.

## 3. Flip the config (soft launch)

```json
"current_update": "u51",   // what the cron generates
"active_update": "u50",    // where the root redirect and updates page point
"updates": {
  "u50": { ..., "status": "archived", "partition": 29 },
  "u51": { "label": "Update 51", "display_name": "Update 51",
           "path_prefix": "u51", "status": "active", "partition": 30 }
}
```

Push. The first `u51` run takes the workflow's bootstrap path (no committed
`output/u51/builds.json` and the live URL returns 404) and seeds an empty
`builds.json`. Do not commit a `u51/builds.json` by hand: a committed copy makes
the workflow treat the update as established and try to download it.

## 4. Populate, then switch the front door

Dispatch the trials one at a time (the concurrency group holds one pending run;
a third dispatch replaces the pending one):

```bash
for id in 1 2 3 5 6 7 8 12 14 15 16 17 18 19; do
  gh workflow run "Generate ESO Builds (Staggered)" -f trial_id=$id
  sleep 20; gh run watch "$(gh run list --limit 1 --json databaseId --jq '.[0].databaseId')" --exit-status
done
```

Grep each run's log for missing-icon warnings; new sets and abilities need
icons in `static/icons`. When all trials are present in `/u51/builds.json`, set
`active_update` to `u51`, push, and let the next run regenerate the root
router, the updates page and the sitemap index.

## 5. Verify

- `https://esobuild.com/` redirects to `/u51/`; `/updates.html` lists U51 as current.
- `/u50/sitemap.xml` still has the frozen page count; spot-check a build page.
- `/sitemap-index.xml` lists u51.
- `gh run list` shows no overlapping runs.
